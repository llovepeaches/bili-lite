## 1. 跨端功能不一致

### 1.1 Windows 端本地数据「存不住」

**不合理之处**

上一版结论写的是「`shared_preferences` 在 Windows 上没有原生实现，登录态退化为仅本次会话有效」。这个结论**是错的**，且被写进了代码注释与 UI 文案里，等于把一个可修的问题描述成了平台限制。

真实情况是 federated 插件矩阵：

| 版本 | Android | iOS/macOS | Windows | Linux | Web |
| --- | --- | --- | --- | --- | --- |
| 2.0.x | ✅ | ✅ | ❌ | ❌ | ✅ |
| 2.1.x | ✅ | ✅ | ✅ | ✅ | ✅ |

`pubspec.yaml` 里写的是 `shared_preferences: ^2.0.15` —— `^2.0.15` 允许解析到 `2.0.x`，一旦解析到没有桌面端实现的版本，桌面端就会因为 `MissingPluginException` 静默退化为「不持久化」。而 `pubspec.lock` 当时恰好锁在 `2.1.1`，所以本地开发看不出来，重新解析依赖就会中招。

**改进方案**

1. `pubspec.yaml` 收紧到 `^2.1.0`，保证六端 federated 实现齐全，并在注释里写清原因；
2. 新增 `core/storage.dart`（`LocalStore`），把「本地存储是否真的可用」变成**可探测的事实**而不是按平台写死的结论；
3. `LocalStore.init()` 捕获插件异常，暴露 `persistent` 与 `unavailableReason`，UI 如实告知用户；
4. 插件不可用时降级为内存存储，保证同一会话内功能仍可用，而不是让各处各自静默失败。

**影响文件**：`pubspec.yaml`、`lib/core/storage.dart`（新增）、`lib/state/app_state.dart`、`lib/state/library_state.dart`、`lib/state/auth_session.dart`、`lib/state/search_history.dart`（新增）

### 1.2 离线 / 在线模式分区条数量不一致

**不合理之处**

分区表存在三份：

| 位置 | 项数 | 缺失内容 |
| --- | --- | --- |
| `state/app_state.dart` 的 `_partitions` | 12 | 国创 / 舞蹈 / 汽车 / 科技… |
| `data/api_client.dart` 的 `_partitions` | 21 | — |
| `server/src/index.js` 的 `PARTITIONS` | 21 | — |

App 的分区条渲染依赖服务端 `/api/meta`；断网或 `OFFLINE=1` 时走 `app_state` 的兜底表。结果是**同一个页面在两种模式下的分区条数量不一样**，用户会以为功能缺失。

**改进方案**

抽出 `core/partitions.dart` 的 `BiliPartitions.items` 作为单一数据源，客户端各处一律引用它；服务端 `PARTITIONS` 保持同序同项。新增单元测试锁定「21 项 / rid 唯一 / 首尾项与服务端一致」，防止后续两边再次漂移。

**影响文件**：`lib/core/partitions.dart`（新增）、`lib/state/app_state.dart`、`lib/data/api_client.dart`、`server/src/index.js`（仅核对，未改）

### 1.3 「能否内嵌官方播放器」有两个真相来源

**不合理之处**

`core/bili_player.dart` 里有 `static bool get canEmbed => kIsWeb;`，但 `PlayerPage` 实际上用的是「`buildOfficialPlayer()` 返回 null 就走 fallback」这个**隐式约定**。能力声明与承载实现分居两个文件，改一处忘另一处就会出现「声称能内嵌、实际返回 null」的错位。

**改进方案**

把能力标记下沉到平台文件，与实现放在一起：

- `player_view_web.dart` → `const bool kCanEmbedOfficialPlayer = true;`
- `player_view_stub.dart` → `const bool kCanEmbedOfficialPlayer = false;`
- `player_view.dart` 条件导出该常量，业务代码只读一个符号；
- 删除 `BiliPlayer.canEmbed` 死代码；
- `PlayerPage` 依据常量决定渲染 iframe 还是 fallback，且即使声明可内嵌、实际返回 null 也照样降级。

**影响文件**：`lib/core/bili_player.dart`、`lib/features/player/player_view.dart`、`lib/features/player/player_view_web.dart`、`lib/features/player/player_view_stub.dart`、`lib/features/player/player_page.dart`

### 1.4 搜索历史用了另一套存储约定

**不合理之处**

`features/search/search_page.dart` 自己维护 `_historyKey` / `_loadHistory` / `_saveHistory` / `_clearHistory`，与收藏 / 历史 / 稍后再看走的是**两套割裂路径**。直接后果：设置页的「清空全部本地数据」漏掉了搜索历史。

**改进方案**

把搜索历史提到 state 层 `lib/state/search_history.dart`，与其它本地数据共用 `LocalStore` 与同一套 key 约定；设置页的清空动作补上 `searchHistory.clear()`。

**影响文件**：`lib/state/search_history.dart`（新增）、`lib/state/globals.dart`、`lib/main.dart`、`lib/features/search/search_page.dart`、`lib/features/settings/settings_page.dart`

## 2. 样式规范不统一

### 2.1 颜色语义没有单一来源

**不合理之处**

同一个「状态色」概念散落在 4 个文件，各写死一份十六进制值：

| 值 | 出现位置 | 语义 |
| --- | --- | --- |
| `0xFF34B27B` | `format.dart`、`shell_page.dart` | 连接正常 |
| `0xFFE9A23B` | `settings_page.dart`、`account_card.dart` | 缓存可用 |
| `0xFFD98032` | 多处 | 需要注意 |
| `0xFF8B8F98` | 多处 | 中性 / 离线 |

`Fmt.sourceColor(String source, bool dark)` 的 `dark` 参数**从未被使用** —— 一个从不生效的开关比没有参数更危险，因为它让人以为颜色会随主题变化。

**改进方案**

- 新增 `core/tokens.dart` 的 `AppStatus`，四个语义色集中定义；
- 删除 `Fmt.sourceColor` 的 `dark` 参数，色值改走 `AppStatus`；
- 所有调用点改为引用语义名。

**影响文件**：`lib/core/tokens.dart`（新增）、`lib/core/format.dart` 及其调用方

### 2.2 字号 / 圆角 / 间距各写各的

**不合理之处**

- **字号**：11 / 11.5 / 12 / 12.5 / 13 / 13.5 / 14 / 15 / 15.5 / 16 / 18 / 19 —— 十几种数值混用，同一行文字在不同页面字号不同；
- **圆角**：8 / 9 / 10 / 11 / 12 / 13 / 14 / 16 / 18 / 20 / 22 / 26 —— 玻璃面板与普通容器的圆角没有明确区分；
- **间距**：随手写的 6 / 10 / 14 / 18 / 22 等，网格对不齐。

**改进方案**

`core/tokens.dart` 中建立三级阶梯，页面只引用语义名：

- `AppFontSize`：`micro 10.5` → `caption 11` → `small 12` → `body 13` → `bodyLarge 14` → `title 16` → `headline 18` → `appBar 19`（8 级，严格递增，有测试锁定）；
- `AppRadius`：`chip 10` → `control 14` → `panel 20` → `sheet 22` → `dock 26` → `pill 999`；
- `AppSpacing`：`xs 4` → `sm 8` → `md 12` → `lg 16` → `xl 24` → `xxl 32`（4 的倍数，便于对齐）。

后续调整主题只需改这一个文件。

**影响文件**：`lib/core/tokens.dart`（新增）+ 全项目调用点

### 2.3 深色模式下出现看不清的浅灰文字

**不合理之处**

每个文件都手写这一行：

```dart
Theme.of(context).brightness == Brightness.dark
    ? AppColors.darkSub : AppColors.lightSub
```

其中 **6 处漏掉了深色分支**，直接写死 `AppColors.lightSub`（浅色底上的浅灰）。结果是深色模式下这些文字几乎不可读 —— 主要集中在「我的」页与设置页的行标签。

**改进方案**

- `tokens.dart` 提供 `extension AppThemeContext on BuildContext`，暴露 `isDark` / `subTextColor` / `primaryTextColor`；
- 所有取次要色 / 主色的位置改为 `context.subTextColor` / `context.primaryTextColor`；
- 设置页的 `_row` 是顶层函数、没有 `context` 参数，改用 `Builder` 包一层拿到 context 后再取色。

**影响文件**：`lib/core/tokens.dart`（新增）、`lib/features/library/library_page.dart`、`lib/features/search/search_page.dart`、`lib/features/settings/settings_page.dart`、`lib/features/shell/shell_page.dart`、`lib/widgets/video_card.dart` 等

## 3. 交互与布局缺陷

### 3.1 首页 `setState called after dispose` 崩溃

**不合理之处**

`home_page.dart` 的 `_load()` 在三处 `await` 之后直接调 `setState`，`catch` 分支同样如此。用户在加载完成前切走页面，就会触发「setState() called after dispose」。

**改进方案**

每个 `await` 之后补 `if (!mounted) return;`，`catch` 分支同样补上。

**影响文件**：`lib/features/home/home_page.dart`

### 3.2 搜索与评论分页失败后会跳过一整页数据

**不合理之处**

搜索「加载更多」与评论「加载更多」在失败时只弹了个提示，**页码没有回退**。用户点重试时会从失败的页码 +1 开始，中间的数据被永久跳过。

**改进方案**

失败时把页码回退（`_page -= 1` / `_pn -= 1`），重试从同一页重新拉取。

**影响文件**：`lib/features/search/search_page.dart`、`lib/features/detail/detail_page.dart`

### 3.3 「清空收藏」看起来像没生效

**不合理之处**

`LibraryState.load()` 只在**有值时**才覆盖 `_data`。清空后再调 `load()`，因为读回来的是「无数据」，`_data` 保持着内存里的旧列表 —— 用户点了清空，界面却还是旧的。

**改进方案**

`load()` 无论读不读到数据都先重置 `_data[kind]`，再按需赋值。

**影响文件**：`lib/state/library_state.dart`

### 3.4 窄屏下悬浮 dock 遮住列表最后一行

**不合理之处**

窄屏使用底部悬浮 dock，列表末尾没有预留空间，最后一行卡片的播放量 / 弹幕数被 dock 盖住。

**改进方案**

新增 `ShellLayout`（`InheritedWidget`）由壳层向下发布 `usesDock` 与 `bottomInset`，列表末尾按此预留高度。之所以不直接按窗口宽度判断，是因为壳层按窗口宽度、页面按自身宽度判断，两边口径不一致时必然错位。

**影响文件**：`lib/core/responsive.dart`、`lib/features/shell/shell_page.dart`、`lib/widgets/video_grid.dart`

### 3.5 加载完成的瞬间整片卡片「跳一下」

**不合理之处**

骨架屏 `LoadingGrid` 把 `childAspectRatio` 写死成 `0.82`，真实网格用的是另一个比例。数据到达、真实卡片替换骨架屏时，整片网格会缩放一下。

**改进方案**

在 `Breakpoints` 里新增 `cardAspectRatio(totalWidth, columns, gutter)`，骨架屏与真实网格共用同一个计算，比例天然一致。

**影响文件**：`lib/core/responsive.dart`、`lib/widgets/state_views.dart`、`lib/widgets/video_grid.dart`

### 3.6 卡片 hover / 按下时整棵子树重建

**不合理之处**

`VideoCard` 的 hover 与 pressed 状态直接放在 `StatefulWidget` 的 `setState` 里，导致封面图、标题、三行统计的整棵子树每次鼠标移动都重建。

**改进方案**

拆成 `_VideoCardState`（只负责装饰层：hover / pressed 动效）与 `_VideoCardContent`（内容层，无状态），装饰变化不再触碰内容。

**影响文件**：`lib/widgets/video_card.dart`

## 4. 代码结构与重复冗余

### 4.1 四份手写确认对话框

**不合理之处**

`library_page.dart`（2 处）、`settings_page.dart`、`account_card.dart` 各自手写 `AlertDialog`，按钮文案、圆角、危险操作用色各不相同 —— 同一个 App 里「删除」看起来像四种操作。

**改进方案**

抽出 `widgets/confirm_dialog.dart` 的 `showConfirmDialog(...)`，统一文案与危险色。

**影响文件**：`lib/widgets/confirm_dialog.dart`（新增）+ 3 个调用方

### 4.2 三份结构雷同的页面头部卡片

**不合理之处**

首页、我的、搜索三处的头部卡片结构完全一样（标题 + 副标题 + 说明文字 + 内边距），但各写一份。

**改进方案**

抽出 `widgets/page_header_card.dart` 的 `PageHeaderCard`，三处共用。

**影响文件**：`lib/widgets/page_header_card.dart`（新增）+ 3 个调用方

### 4.3 两份 Logo 实现

**不合理之处**

`shell_page.dart` 有 `_Logo`（38pt），`home_page.dart` 有 `_GlassLogo`（28pt），图形画法一致、尺寸不同。

**改进方案**

抽出 `widgets/app_logo.dart` 的 `AppLogo`，尺寸由参数决定。

**影响文件**：`lib/widgets/app_logo.dart`（新增）+ 2 个调用方

### 4.4 三处重复的「记历史 → 跳详情」

**不合理之处**

首页、搜索、我的三处各自写了一遍「先 `library.addHistory(v)`，再 `Navigator.push` 详情页」的组合逻辑，任何一处漏掉记历史都会造成浏览记录缺失。

**改进方案**

抽出 `core/navigation.dart` 的 `openVideoDetail(context, video)` 与 `toggleLibraryItem(...)`。同时因为项目锁在 Flutter 3.0（无 `BuildContext.mounted`），统一用 `NavigatorState.mounted` 判断。

**影响文件**：`lib/core/navigation.dart`（新增）+ 3 个调用方

### 4.5 接口路径表是死代码

**不合理之处**

`ApiConfig.endpoints` 定义了一张完整的路径表，但 `BiliRepository` 里全部硬编码 `'/api/feed'`、`'/api/rank'`…… 这张表从未被调用。改路径时只改常量不改调用点，是最容易漏的坑。

**改进方案**

- 路径表抽到 `core/api_paths.dart` 的 `ApiPaths`（纯 Dart，不依赖 Flutter）；
- `Repository` 全部改为 `ApiConfig.endpoint('feed')` 形式；
- 具名 const 字段保证 `case ApiPaths.feed:` 这类分支可写成编译期常量（Dart 的 `case` 标签不接受函数调用结果）。

**影响文件**：`lib/core/api_paths.dart`（新增）、`lib/core/config.dart`（转发）、`lib/data/repository.dart`、`lib/data/api_client.dart`、`lib/data/bili_direct.dart`

### 4.6 `verify_live.dart` 从来跑不通

**不合理之处**

`tool/verify_live.dart` 的注释写着「开发期自检脚本」，实际执行必然失败：

```
Error: Not found: 'dart:ui'
```

原因是它 import 的 `bili_direct.dart` → `core/config.dart` → `package:flutter/foundation.dart`，而纯 Dart VM 里没有 `dart:ui`。也就是说，**原生端直连链路从来没有被这条脚本真正验证过**。

**改进方案**

把与运行环境无关的路径表抽到 `core/api_paths.dart`（纯 Dart），`bili_direct.dart` 只依赖它，不再牵动 Flutter 框架。修复后该脚本实测 **6/6 接口返回实时数据**。

**影响文件**：`lib/core/api_paths.dart`（新增）、`lib/data/bili_direct.dart`、`lib/core/config.dart`

### 4.7 本地存储逻辑散落 4 处

**不合理之处**

`app_state.dart`、`library_state.dart`、`search_page.dart`、`auth_session.dart` 各自写了一遍 `SharedPreferences.getInstance()` + try/catch，错误处理口径不一（有的静默吞掉、有的抛异常）。

**改进方案**

新增 `core/storage.dart` 的 `LocalStore` 单例门面，统一 14 个读写方法 + JSON 列表辅助 + 内存兜底 + 能力探测。

**影响文件**：`lib/core/storage.dart`（新增）+ 4 个调用方

## 5. 平台配置与打包

### 5.1 Android 正式包允许任意域名走明文 HTTP

**不合理之处**

`AndroidManifest.xml` 里 `android:usesCleartextTraffic="true"`，正式包也生效。原生端直连 B 站走的是 HTTPS，明文只在「连本机 / 局域网 BFF 调试」时需要 —— 而那条链路只存在于 debug 构建。

**改进方案**

- `src/main/AndroidManifest.xml` 改为 `usesCleartextTraffic="false"`，并声明 `xmlns:tools`；
- 新建 `src/debug/AndroidManifest.xml`，用 `tools:replace="android:usesCleartextTraffic"` 把 debug 包单独放开明文；
- release 构建不合并 debug 目录，因此正式包保持关闭。

> 顺带修掉一个自己引入的真实错误：最初的改动把 XML 注释写在了 `<application>` 开始标签的属性列表中间（标签要到第 17 行才闭合），XML 不允许在开始标签内部出现注释，导致 manifest 无法解析、构建直接失败。已把注释移到 `<application>` 元素之外。`src/debug/AndroidManifest.xml` 里的 `--dart-define` 注释同样非法（XML 注释内不能出现连续两个连字符），已改写。

**影响文件**：`app/android/app/src/main/AndroidManifest.xml`、`app/android/app/src/debug/AndroidManifest.xml`（新增）

### 5.2 iOS 全局放开 ATS

**不合理之处**

`Info.plist` 里 `NSAllowsArbitraryLoads = true` 全局放开明文 HTTP，这类配置会被 App Store 审核拒。

**改进方案**

移除 `NSAllowsArbitraryLoads`，改为 `NSAllowsLocalNetworking = true` + `NSExceptionDomains` 精确白名单（`localhost` / `127.0.0.1`），只对调试用的本地服务放开。

**影响文件**：`app/ios/Runner/Info.plist`

### 5.3 CI 缺少质量守门

**不合理之处**

流水线只负责「编译」，`flutter analyze` 与 `flutter test` 一次都没跑过。任何静态错误都要等装到手机上才发现。

**改进方案**

- 新增 `checks` job：`flutter analyze --fatal-infos --fatal-warnings` + `flutter test` + 服务端 `npm run check` + `npm run verify:oauth`；
- `android` / `windows` / `web` 三个 job 加上 `needs: [checks]`，静态检查不通过就不产出安装包。

**影响文件**：`.github/workflows/build-installers.yml`

### 5.4 `verify_web.cjs` 把合法的降级模式判为失败

**不合理之处**

脚本只在数据源为 `live` / `cache` / `bili` 时判成功，而 BFF 处于 `MOCK_MODE` 或上游被风控时返回的 `mock` 快照是**合法降级**，链路本身是通的 —— 脚本却因此永远红着。

**改进方案**

区分「链路通不通」和「数据新不新」两件事：`live` / `cache` / `bili` 判为已连实时数据，`mock` / `static` 判为链路正常但数据来自降级快照，两者都不算失败；只有既没拿到 feed 又没拿到 health 才判失败。

**影响文件**：`app/tool/verify_web.cjs`

## 2. 架构改造

### 2.1 集中路由层（消灭裸 `MaterialPageRoute`）

新增两个文件：

* `lib/core/route_args.dart` —— **纯数据**的路由名与参数类，不 import 任何 UI，避免 router ↔ features 循环依赖
* `lib/router/app_routes.dart` —— `AppRouter.generate` 集中路由表

```dart
class AppRouteNames {
  static const String videoDetail = '/video-detail';
  static const String player = '/player';
}
```

`MaterialApp` 挂 `onGenerateRoute: AppRouter.generate`，跳转统一走 `Navigator.pushNamed`。这样新增页面只需改一处路由表，不用全局搜 `push`。

### 2.2 页面拆分 controller / view 两层

| 改造前 | 改造后 | 行数变化 |
| --- | --- | --- |
| `home_page.dart` | `home_controller.dart` + `home_view.dart` | 280 → 拆两份 |
| `detail_page.dart` | `detail_controller.dart` + `detail_view.dart` | 756 → 拆两份 |
| `search_page.dart` | `search_controller.dart` + `search_view.dart` | 313 → 拆两份 |
| `library_page.dart` | `library_controller.dart` + `library_view.dart` | 175 → 拆两份 |
| `settings_page.dart` | `settings_controller.dart` + `settings_view.dart` + `settings_sections.dart` | 496 → 拆三份 |
| `account_card.dart` | `account_controller.dart` + `account_view.dart` | 439 → 拆两份 |

约定：**controller 只管「做什么」（数据加载、分页、状态变更），view 只管「长什么样」**。需要弹窗的动作由 view 传入 `BuildContext`，controller 自身不持有任何 Widget 引用，避免生命周期泄漏。

### 2.3 用户偏好层

新增 `lib/state/preferences.dart`（`AppPrefs extends ChangeNotifier`），统一管理：

* 导航项顺序与显隐（`AppSection` 枚举）
* 卡片样式（`CardStyle` 枚举：沉浸式 / 紧凑型）
* 滚动时是否隐藏底部 dock

全部经 `LocalStore.instance` 门面持久化。导航项用 **枚举本身**（而非下标）记忆选中项 —— 用户调整顺序后按下标记忆会选错页面。

## 3. 界面改造

### 3.1 沉浸式视频卡片

新增 `CardStyle` 枚举，两种样式共用同一个 `VideoCard`：

* **沉浸式**（默认）：弹幕数叠在封面左下角，与右下角时长左右呼应；封面下方只留标题 / UP 主 / 播放量三行，一屏能看更多内容
* **紧凑型**：统计信息全部排在封面下方，文字更易读

关键细节：沉浸式的文字区高度更矮（88 vs 104），`Breakpoints.cardAspectRatio` 新增可选 `textArea` 参数，**骨架屏与真实网格必须用同一算法**，否则加载完成的瞬间整片卡片会缩放一次。

### 3.2 分区浮层菜单

21 个分区原先挤在一条横向滚动条里，名字一多就点不准。新增 `widgets/partition_sheet.dart`：

* 毛玻璃浮层（不是系统默认 Material 底部弹窗）
* 「图标 + 名称」网格，每分区专属 Material 图标与主色
* 面板底部压一层近不透明实色板 —— 玻璃太透会让下方卡片文字与浮层文字叠在一起

> **为什么不用 emoji**：emoji 依赖系统字体，桌面 Web 与部分 Linux 环境缺字形会渲染成豆腐块。Material 图标随 Flutter 走，全端一致。

### 3.3 详情页结构重排

按 MiniBili 的信息层级整体重排：

```
工具胶囊组（收藏 / 稍后再看 / 播放 / 原站）
  → 播放器
  → 「详情 / 评论」分段控件
  → 标题
  → 统计行（播放 / 弹幕 / 评论 / 点赞 / 投币 / 收藏 / 分享）
  → UP 主卡片（头像 + 昵称 + UID + 查看主页）
  → 四连互动栏（点赞 / 投币 / 收藏 / 分享 + 稍后再看）
  → 折叠简介卡片
  → 话题标签胶囊
  → 分 P 列表
```

宽屏改为「左详情 + 右评论」双栏。Flutter 3.0 没有 `SegmentedButton`，自绘了 `GlassSegmented`。

### 3.4 可配置导航

* `AppSection` 枚举替代原先写死在 `shell_page.dart` 里的私有 `_NavItem` 列表
* 设置页新增「界面与导航」区块：卡片样式切换、导航入口编辑器（上下移动排序 + 隐藏/显示）、滚动收起底部导航开关
* 用户改了导航顺序后用 `ValueKey` 重建 `IndexedStack`，否则旧子页面会按旧下标留在原位

## 4. 本轮修复的真实缺陷

以下都是本轮实际发现并修复的问题，不是预防性改动。

### 4.1 首页整页蒙一层白纱

**现象**：AppBar 标题、TabBar、卡片文字全被半透明白层盖住；搜索页 / 设置页 / 我的页正常。

**根因**：`AnimatedBuilder(animation: _controller)` 包裹了整个 `Scaffold`。每次 `notifyListeners()` 都重建 AppBar，其 `flexibleSpace: GlassBar()` 的镜面高光动画（`_BarPainter` sweep）与卡片玻璃 sheen 反复重播，累积成一层白纱。

**修法**：`home_view.dart` 与 `detail_view.dart` 的 AnimatedBuilder **只包 body**，AppBar 保持静态；`SourceBadge` / `_ToolGroup` 用局部 AnimatedBuilder 订阅；首页改用 `TabController` 驱动 TabBar。

### 4.2 卡片上显示 `[object Object]`

**现象**：所有视频卡片左上角的推荐理由标签显示 `[object Object]`。

**根因**：上游 `rcmd_reason` 字段有时是对象 `{ content: '百万播放' }`，`normalize.js` 的 `cleanText` 直接 `String(v)` 就把这串脏字符串塞进了卡片。

**修法**：三端统一收敛 ——

* `server/src/normalize.js` 新增 `reasonText()`，递归处理字符串 / 对象 / 对象数组
* `app/lib/data/bili_direct.dart` 新增 `_reasonText()`，直连通道逻辑对齐
* `app/lib/data/models.dart` 的 `_s()` 增强：遇到 Map / List 时按 `content → reason → text → name` 顺序取第一个非空值

修复后卡片显示的是真实标签（"百万播放"、"1万点赞"、"已关注"）。

### 4.3 详情页在桌面浏览器上几乎读不到内容

**现象**：1080×760 的桌面视口下，16:9 的播放器占满整个宽度（高达 607px），详情内容被推到屏幕外，还要再嵌一层滚动。

**修法**：两处调整 ——

* `Breakpoints.detailTwoColumn` 阈值从 1100 下调到 **900**：宽桌面走双栏
* 窄屏（单栏）下用 `ConstrainedBox` 把播放器高度限制在可用高度的 50% 以内，保证下方内容始终露出来

### 4.4 分区浮层的两个渲染问题

* **浮层透底**：玻璃面板太透，下方卡片文字与浮层文字重叠不可读 → 面板底部压一层近不透明实色板
* **网格行距被拉大**：`GridView` 放在 `Flexible` 里会被撑到剩余高度 → 改用 `Wrap` + `LayoutBuilder` 精确排布，外层套 `SingleChildScrollView` 兼容小屏

# 第三轮改造：应用内播放、弹幕、登录入口前置与刷新修复

> 本轮来自一条真实的用户反馈：**「应用内刷新不了，增加登录，应用内播放、弹幕等」**。
>
> 拆成四件事，逐项落地并验证：
> 1. **刷新失效** —— 下拉刷新 / 「换一批」拿不到新内容；
> 2. **登录找不到** —— 账号卡片藏在设置页最底部，未配置凭证时入口停用，用户以为应用不能登录；
> 3. **应用内播放** —— 之前只有官方 iframe 外链播放器，不解析播放地址；
> 4. **弹幕完全没实现**。

## 1. 刷新失效的根因与修复

### 1.1 根因（两个叠加）

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | `home_controller.dart` | `HomeController.load(force: true)` 把 `_freshIdx` **重置为 1**。但 B 站的 `fresh_idx` 就是「换一批」的游标，重置回 1 必然拿到与上次**完全相同**的一批稿件。 |
| 2 | `server/src/index.js` | `/api/feed` 按 `feed:${ps}:${freshIdx}` 缓存 60 秒。即使游标变了，60 秒内仍命中同一份缓存。 |

### 1.2 修法

* 客户端：`force` 时**递增** `_freshIdx`（而不是重置），并带上 `skip_cache=1`；
* 服务端：`cached()` 新增 `skipCache` 分支——绕过新鲜缓存重新取数，但**请求失败时仍退回陈旧缓存 / 离线快照**，不让用户因为一次上游抖动看到空列表；
* 直连通道（原生端不依赖 BFF）：`BiliDirect._cached()` 同样新增 `skipCache` 命名参数。

实测：`fresh_idx=1` 与 `fresh_idx=2&skip_cache=1` 返回完全不同的稿件列表。

回归测试：`test/home_refresh_test.dart` 断言「换一批会递增 fresh_idx 并强制绕过缓存」。

## 2. 应用内播放

### 2.1 为什么不能直接用 B 站的地址

B 站播放地址接口是 `/x/player/playurl`，返回的 `durl` 直链有两个坑：

* **防盗链**：CDN（`*.bilivideo.com`）校验 `Referer` 与访客身份，缺失就 403；
* **CORS**：Web 端 `<video src>` 直接指向 CDN 会被跨域策略拦掉。

而 `fnval=16`（DASH）返回音视频分离的 m4s，需要 MSE/ExoPlayer 合流器才能播，六端行为不一致——**放弃**。最终选 `fnval=1` 的 `durl`：单文件 mp4，渐进式下载、可边下边播。

### 2.2 服务端：新增两个接口

| 接口 | 作用 |
| --- | --- |
| `GET /api/playurl?bvid=&cid=&qn=` | 解析 mp4 直链，返回 `url` / `quality` / `qualityLabel` / `size` / `timelength` / `acceptQuality` |
| `GET /api/stream?bvid=&cid=&qn=` | **视频流反向代理**：服务端带正确 UA / Referer / 访客身份去 CDN 取流，支持 `Range`（拖进度条必须有），透传 206 / `Content-Range` |

`/api/stream` 只允许 `*.bilivideo.com` 域名（避免被当成任意 URL 代理，SSRF）；`cached()` 缓存直链 5 分钟，因为直链本身十几分钟就过期。

实测：`curl -r 0-1023 /api/stream` 返回 `206 Partial Content`、`Content-Range: bytes 0-1023/13837201`。

### 2.3 客户端：`VideoSurface` 抽象

```
lib/features/player/
├── video_surface.dart        平台无关接口 + 条件导出工厂
├── video_surface_native.dart 原生端：video_player（Texture）
├── video_surface_web.dart    Web 端：自建 DOM 播放器
├── player_controller.dart    取数 + 弹幕时间轴 + 播放状态
├── danmaku_timeline.dart     弹幕轨道分配（纯 Dart，两端共用）
├── danmaku_layout.dart       弹幕排版公式（纯 Dart，两端共用）
├── danmaku_overlay.dart      原生端弹幕画布
└── player_page.dart          播放页（画面 + 控制条 + 弹幕设置）
```

**为什么 Web 端不用 `video_player_web`**：它的实现是 `HtmlElementView`，也就是一个真实 DOM 元素。浏览器的合成顺序决定它永远盖在 Flutter 画布之上——弹幕画在 Flutter 里会被视频挡得一点都看不见。所以 Web 端改成把 `<video>` 与弹幕 `<canvas>` 放进同一个容器 div，两者都是 DOM 元素，canvas 在后自然盖在 video 上。

**视频播放器依赖版本**：`video_player: 2.3.0`（**精确版本，不能用 caret**）。`^2.3.2` 会解析到 2.6.1，而 `video_player >= 2.7.0` 要求 Dart ≥ 2.18、`video_player_web >= 2.0.17` 要求 Dart ≥ 2.19，与项目锁定的 Dart 2.17 冲突；`2.3.2` 本身不存在于 pub。`2.3.0` 的求解结果是 video_player 2.3.0 / platform_interface 5.1.4 / web 2.0.15 / android 2.4.3 / avfoundation 2.3.9。

### 2.4 弹幕

* **上游格式**：`/x/v1/dm/list.so` 返回的是 **deflate(raw) 压缩的 XML**，不是 protobuf 也不是未压缩 JSON。服务端 `zlib.inflateRawSync` 解压后解析成 JSON；直连通道由 Dart 端 `ZLibDecoder(raw: true)` 解压（`lib/data/inflate.dart` 用条件导入分离 Web / 原生）。
* **XML 结构**：`<d p="时间(秒),模式,字号,颜色,发送时间,随机种子,用户ID,行ID">文本</d>`，模式 1=滚动、4=底部固定、5=顶部固定。
* **轨道分配**：这是 1980 年代弹幕系统的老问题——同一时刻的滚动弹幕会从右向左穿过整屏，不做轨道分配就会互相「盖脸」。`DanmakuTimeline` 维护每条轨道的「空闲时刻」，贪心找一条空闲时刻 ≤ 出现时刻的轨道，找不到就新开一条；顶部 / 底部固定弹幕各自独立轨道池。
* **平滑播放位置**：`video_player` 每 500ms 才回报一次位置，直接拿来驱动弹幕会一顿一顿。`PlayerController` 用本地时钟在两次回报之间做线性外推，每次拿到新位置时重新校准。
* **渲染分层**：原生端弹幕是 Flutter 画布画在 Texture 之上；Web 端画在 DOM canvas 上。**排版公式两端共用** `DanmakuLayout`，同一视频在手机和浏览器上观感一致。

实测（Web 端）：`<video>` 正常解码 1280×720、`readyState=4`，弹幕 canvas 持续有上万个非透明像素，滚动弹幕 / 顶部固定弹幕 / 颜色 / 字号均正确。

### 2.5 顺带修掉的 Android 构建失败

引入 `video_player` 之后，CI 的 Android job 直接挂了——**不是代码问题，是 Android 工具链版本**：

```
Execution failed for task ':app:checkReleaseAarMetadata'.
  Dependency 'com.google.android.exoplayer:exoplayer-core:2.18.5'
  requires 'compileSdkVersion' to be set to 33 or higher.
  Compilation target for module ':app' is 'android-31'
```

原因链条：`video_player_android` 2.4.3 自带 ExoPlayer 2.18.5，它要求宿主 `compileSdk ≥ 33`；同批被 pub 求解升上去的 `url_launcher_android` 6.0.26 也要求 33。而 Flutter 3.0 模板给的是 `compileSdkVersion 31`（由 `flutter.compileSdkVersion` 决定），AAR metadata 校验阶段直接拦下。

修法（3 处）：

| 文件 | 改动 |
| --- | --- |
| `app/android/app/build.gradle` | `compileSdkVersion` 31 → **33**（硬编码覆盖 `flutter.compileSdkVersion`） |
| `app/android/build.gradle` | AGP `7.1.2` → **7.2.2**（首个官方支持 compileSdk 33 的版本；要求 Gradle ≥ 7.3.3，仓库 wrapper 是 7.4，满足） |
| `.github/workflows/build-installers.yml` | 安装 `platforms;android-33` + `build-tools;33.0.2` |

**只抬 compileSdk，不动 `targetSdk` / `minSdk`**：`targetSdk` 保持 31，避免引入 Android 13 的运行时行为变化（通知权限、PendingIntent 可变性等）；`compileSdk` 只影响编译期 API 面，抬高它不会改变运行时行为。`compileSdk ≥ targetSdk` 是合法组合。

CI 日志实测确认：`package: name='com.bililite.bililite' versionCode='5' versionName='1.5.0' compileSdkVersion='33' compileSdkVersionCodename='13'`，产出 `app-release.apk` 20.3MB。

# 第四轮改造：扫码登录主通道与授权服务降级

> 本轮来自一条带截图的用户反馈：**「修复这个 b 站登录问题」**。
> 截图里账号面板显示「授权服务不可用」，登录入口整体不可用。
> 给出的三条修复路线中，用户选择 **「加扫码登录（推荐）」**。

## 1. 根因：不是配置错，是架构错

| # | 层 | 问题 |
| --- | --- | --- |
| 1 | 官方 OAuth 2.0 | `client_secret` 只能留在服务端换 token，而独立安装包（APK / exe / Web 静态产物）里根本没有这个服务端。没有开放平台凭证 + 自建 BFF 时 `configured=false`，登录链路从第一步就走不通。 |
| 2 | 默认地址 | `ApiConfig.baseUrl` 在 Android 上是 `http://10.0.2.2:8787` —— 这只是**模拟器**指向宿主机的别名，真机不可达。 |
| 3 | 明文策略 | release 清单 `android:usesCleartextTraffic="false"`，Android 9+ 会直接拦截局域网 `http://` 请求。 |
| 4 | 状态机 | `AuthSession.refreshConfig()` 探活 `/api/oauth/config` 失败就把整个账号状态压成 `unavailable`，UI 因此把两路登录一起隐藏，用户看不到任何可用方式。 |

前三条决定「官方 OAuth 不可能成为普通用户的默认登录方式」，第四条把这个事实放大成「整个账号面板像坏了」。
只修可达性无法解决第 1 条，因此按用户选择新增一条**不依赖服务端**的官方扫码登录链路。

## 2. 方案：扫码登录主通道，官方 OAuth 降级为备用

### 2.1 链路

```text
原生端（Android / iOS / 桌面）            B 站
   │ ① GET passport.bilibili.com/.../qrcode/generate      │
   ├────────────────────────────────────────────────────►│ → url + qrcode_key
   │ ② QrImage 渲染 url，手机 B 站 App 扫码并确认           │
   │ ③ 每 2s GET .../qrcode/poll?qrcode_key=               │
   ├────────────────────────────────────────────────────►│ → 86101 未扫 / 86090 待确认 / 0 成功
   │ ④ 成功时从 Set-Cookie 与回调 URL 取登录 Cookie         │
   │ ⑤ GET api.bilibili.com/x/web-interface/nav（带 Cookie）│ → 昵称 / 头像 / mid
   │ ⑥ Cookie 存入本机 SharedPreferences                   │
```

Web 端浏览器受同源策略限制不能直连 B 站登录域，改走同源 BFF `/api/qr/generate`、`/api/qr/poll`、`/api/qr/nav`
做**纯转发代理**：不缓存、不落盘、不打印 Cookie，响应统一 `Cache-Control: no-store`。
原生端完全不经过 BFF。

### 2.2 平台分流与边界

| 平台 | 扫码请求路径 | 说明 |
| --- | --- | --- |
| Android / iOS / 桌面 | 直连 `passport.bilibili.com` + `api.bilibili.com` | 带完整 UA / Referer |
| Web | 同源 `/api/qr/*` → BFF `qr_proxy.js` → B 站 | UA / Referer 由服务端注入；浏览器不允许 `http.Client` 设置 `User-Agent` / `Referer`，故 `QrLoginApi._headers` 按 `kIsWeb` 分流 |

### 2.3 关键实现点

* **Cookie 百分号编码保持**：`Uri.queryParameters` / `URLSearchParams.get()` 会自动 URL 解码，把 `SESSDATA` 里的 `%2C` / `%2A` 还原成 `,` / `*`，Cookie 直接失效。Dart 与 Node 两端都改成切**原始 query 字符串**，只 `decodeURIComponent` key，value 保留原编码。
* **半套凭证拒绝**：`buildCookie()` 必须同时拿到 `SESSDATA` 与 `bili_jct` 才返回，否则返回空串，避免存下一份不可用的身份。
* **统一身份门面**：`AccountIdentity` 用 `Listenable.merge([qrSession, authSession])` 合并两路状态，扫码优先。即使 `AuthSession` 因 BFF 不可用进入 `unavailable`，只要 `qrSession.signedIn`，首页顶栏和「我的」页仍显示已登录。
* **退出登录双清**：`QrAccountCard` 的退出同时调用 `qrSession.signOut()` 与 `authSession.signOut()`，不留半套凭证。
* **弹层生命周期**：`QrSession.cancel()` 在弹层关闭时停止 2 秒轮询，避免后台持续打 B 站。
* **二维码库版本**：`qr_flutter 4.1.0` 要求 Dart ≥ 2.19.6 / Flutter ≥ 3.7，与本项目 Flutter 3.0 / Dart 2.17 冲突；锁定 `4.0.0`（`sdk >=2.12.0 <3.0.0`，依赖纯 Dart 的 `qr ^2.0.0`）。

## 3. 启动提速

改造前（关键路径全是串行 await）：

```text
WidgetsFlutterBinding → library.load → searchHistory.load → ServerConfig.init
→ appState.init（内含 fire-and-forget 探测）→ qrSession.init
→ authSession.init → refreshConfig → GET /api/oauth/config（15s 超时）
→ runApp  ← 首屏在这里才出现
```

改造后：

```text
LocalStore.init（单独 await，见下）→ Future.wait([6 个纯本地初始化]) → runApp ← 首屏
                                                                        └→ 后台并行：
                                                                           BFF 健康探测
                                                                           OAuth 备用通道探活
                                                                           更新检查（12h 节流）
                                                                           Web OAuth ticket 领取
```

* **为什么要单独 await `LocalStore.init()`**：它的 `init()` 一进入就把
  `_initialized` 置 true 才去 await `SharedPreferences.getInstance()`。若把它和其它
  初始化一起并发，别的调用方会立刻短路返回、读到尚未赋值的 `_prefs` 而退化成内存态。
  先单独 await 一次，后续 6 个任务里的重复 `init()` 才会安全短路。
* `AuthSession` 拆出 `initLocal()`（只 `LocalStore.init()` + `_restore()`，不发网络），
  `init()` 保留为 `initLocal() + refreshConfig()` 供后台任务与测试使用。
* `AppState.init()` 去掉内部的 `refreshServerInfo()`，只负责本地偏好。
* `_guarded()` 给每个后台任务套 8s 上限并吞掉异常；离线 / BFF 未部署是独立安装包常态，
  设置页保留「重新检测」手动入口。
* `kDebugMode` 下打印 `[startup] 首屏就绪 XXms`，便于真机排查。
* `test/startup_test.dart` 用可注入的计数 HTTP 客户端（`OAuthApi.debugClient`，
  `@visibleForTesting`）断言 `initLocal()` 的请求数为 0，`init()` 的探活失败会落到
  `unavailable` 而不抛出。

## 10.1 新增三种 B 站 Web 登录方式

在原有扫码登录（主通道）与官方 OAuth（高级备用）之外，新增：

| 通道 | 数据层链路 | 可用性 |
| --- | --- | --- |
| 账号密码 | `web/key` → 纯 Dart RSA（PKCS#1 v1.5）加密 → `web/login` | 受极验滑块限制 |
| 短信验证码 | `captcha` → `sms/send` → `login/sms` | 受极验滑块限制 |
| Cookie 登录 | `normalizeCookie()` → `nav` 校验 → 写入本机 | 完整可用 |

**诚实边界**：B 站对 Web 密码 / 短信登录强制极验滑块，`validate` / `seccode`

**绝不伪造登录态、绝不把失败包装成成功**。

* 四条通道产物是同一份 B 站 Web 登录 Cookie，统一经
  `QrSession.applyCookie(cookie, LoginMethod)` 落地，不新增第四套身份状态；
  `LoginMethod` 随登录态持久化，退出时重置为扫码。
* 手工粘贴的 Cookie **必须**先经 `nav` 校验有效才写入本机；校验不通过
  绝不保存、绝不显示「已登录」。`normalizeCookie()` 强制要求
  `SESSDATA` + `bili_jct`，并按固定白名单顺序输出（保留 `%2C` 等原始编码）。
* Web 端 CORS 限制由新增的 `server/src/passport_proxy.js` +
  `/api/passport/*` 同源转发解决：只做协议转发、业务码原样透传、

## 12.5 发版过程中的四个坑（都值得记下来）

1. **仓库 Actions 默认权限是只读**：`actions/permissions/workflow` 返回

2. **本地与远端历史分叉**：远端那 11 条提交与本地对应提交 message 逐条一致，

   的时机提前，最终树一致。处理方式是 `git merge origin/main` 并在冲突处
   全取本地版 —— 合并结果相对远端是单向 `+8980 / -185`，删除全部落在本轮
   改过的文件内，**没有 force push**。
3. **`github.com` 的 DNS 被污染**：`getent hosts github.com` 解析到
   `57.155.223.240`，HTTPS 直接超时；但 `api.github.com` 正常。把
   `github.com` 映射到 GitHub 真实 IP（`/etc/hosts` 与 `~/.user_hosts`）后
   立即恢复，TLS 校验照常通过。
4. **git 长连接被重置**：push / fetch 频繁报
   `Recv failure: Connection reset by peer` 与

   `http.lowSpeedLimit=0` + 多次重试可稳定通过（fetch 第 6 次成功）。
   另：重试循环里**不要用管道**（`git push | tail`），管道的退出码是
   `tail` 的 0，会把失败误判成成功 —— 本轮第一次推送就是这样被"假成功"的。

## 13.1 需求与做法

## 13.2 为什么不用 `PageView`，也不用原来的 `IndexedStack + onHorizontalDragEnd`

- **`PageView`**：离开视口的子树会被销毁，首页的滚动位置、搜索页已输入的
  关键词都会丢；而且它会把水平拖拽手势整个吃掉，页面内部的横向滚动小控件
  （首页的分区横条）就滑不动了。
- **原来的 `IndexedStack + onHorizontalDragEnd`**：切页是「瞬间跳变」，
  没有跟手过程，滑动过程中底栏高光也不会提前预告下一页，手感生硬。

`SwipeDeck` 用 `Stack` + `Transform.translate` 自己实现平移，页面始终挂载
（`Offstage` 只停绘制、不销毁状态），因此滚动位置与输入内容全部保活。

## 13.3 三个踩过的坑

1. **位移符号反了**：向左拖时 `delta.dx` 为负，若直接除以宽度，
   `fraction` 会算成负值，判定成「上一页」，第一页左滑因越界直接回弹，
   表现为「怎么滑都切不过去」。正确写法是 `fraction = -accum / width`：
   正值代表「正在往下一页走」。见 `swipe_deck.dart` 的 `_handleDragUpdate`。
2. **预览阈值与提交阈值必须一致**：高光预览原本按 0.5 判定、提交按 0.28，
   会出现「高光在第二页、页面还在第一页」的错位。现在两者共用
   `_commitThreshold = 0.28`，高光先一步挪过去，回弹时再挪回来。
3. **不能同时给 `SwipeDeck` 挂 `ValueKey` 和 `GlobalKey`**：`GlobalKey`
   会被 `ValueKey` 顶掉，`currentState` 永远拿不到。改成**受控索引**：
   外部（底栏点击 / 返回键）改 `index` → `didUpdateWidget` 里动画过去；
   用户滑动 → 吸附完成后 `onIndexChanged` 上报 → 外部更新 `index`。
   拖动过程中另走 `onIndexPreview`，只更新高光不提交页面切换。

# 第十轮：底栏双件式重构 —— 搜索独立到右侧（v0.1.2）

## 14.1 需求

> 「底栏的搜索放到右边，进行分开（像iOS那样）」

iOS 26 的底栏不是「一整条等分的标签栏」，而是**双件式**结构：左边一枚装着
标签组的玻璃胶囊，右边一枚**浮起的独立圆形动作按钮**（Safari 的分享、
Music 的更多）。本轮把「搜索」从前者拆出来，归入后者。

## 14.2 做法对照表

| 文件 | 改动 |
| --- | --- |
| `app/lib/core/nav_section.dart` | `AppSection` 新增 `standalone` 字段，`search` 标记为 `standalone: true`，并写清「独立入口」的语义。 |
| `app/lib/state/preferences.dart` | 新增 `tabSections` / `standaloneSections` 两个派生列表；`moveSection` 改为**同组内**移动（独立入口不参与标签组排序）；`toggleSection` 恢复时放回同类别末尾，保持「独立入口在最右」。 |
| `app/lib/widgets/liquid_dock.dart` | 重写为双件式：`LiquidGlassDock` 拆成 `_GlassShell`（共用玻璃外壳）+ `_CapsuleContent`（胶囊内标签组）+ `_StandaloneButton`（右侧圆形按钮）。新增 `_CircularFlow` / `_CircularFlowPainter` —— 高光**绕圆周**游走。 |
| `app/lib/features/shell/shell_page.dart` | 底栏改用新 API（`tabs` / `standalone` / `active`）；`_sections` 改为「标签组在前 + 独立入口在后」的拼接，保证**视觉顺序 == 滑动顺序**；`_active` / `_dockIndex` 语义统一为「按 `AppSection` 记忆」。 |
| `app/lib/features/settings/nav_config_editor.dart` | 拆成「标签组（底栏胶囊内）」与「独立入口（底栏右侧）」两组展示；独立入口不提供排序箭头。 |

## 14.3 三个设计取舍

1. **两件玻璃各自带一层 `BackdropFilter`**：一开始图省事，在外层包一个
   `BackdropFilter` 罩住整行，结果胶囊和圆按钮的背景模糊糊成一整块，
   边界丢了。改成每件玻璃自己包一层，模糊才贴着各自的轮廓走 —— 这也是
   iOS 那种「两块分离的玻璃」观感的来源。
2. **胶囊内边距只留横向**：最初上下各留 6px，标签组的「图标 44 + 间距 3 +
   文字 12 = 59」比可用高度（62 − 12 = 50）高，渲染直接 overflow。
   现在纵向由内容自己占满胶囊高度，横向留 8px 做呼吸位。
3. **滑动页序必须跟视觉顺序一致**：如果底栏视觉上是「首页 / 我的 / 设置 /
   搜索（最右）」，而滑动页序还是旧的 `prefs.sections` 顺序，用户从
   「设置」左滑就会跳到别处。`AppPrefs` 现在把 `standalone` 入口固定排到
   列表末尾，壳层按「标签组 + 独立入口」拼接，视觉与手势一一对应。

## 14.4 `_CircularFlow` 的实现取舍

`extractPath()` 做描边 —— Flutter Web 的 html renderer 会把抽出来的 path

横向流动亮带是同一个节奏。

# 第十五轮：真·液态玻璃 —— 从「手绘模拟」升级到「真实采样 + 透镜折射」

> 用户给出的 Compose 参考实现：
>
> ```kotlin
> val 背景 = rememberLayerBackdrop { drawRect(背景颜色); drawContent() }
> 主导航主机(修饰符 = 修饰符.layerBackdrop(背景))
> 盒子(
>     修饰符.safeContentPadding().背景(
>         背景 = 背景, shape = { CircleShape },
>         影响 = { 活力(); Blur(4F.dp.toPx()); 镜头(16F.dp.toPx(), 32f.dp.toPx()) },
>         onDrawSurface = { drawRect(Color.White.copy(alpha = 0.5f)) }
>     ).身高(64.dp).fillMaxWidth().align(对齐.BottomCenter)
> )
> ```

这一轮把底栏的玻璃从「自己画渐变假装是玻璃」改成**真的去采样背后内容**，
再对它做**真的折射**。参考实现里的四个要素逐一落到了 Flutter 上。

## 15.1 Compose → Flutter 的语义映射

| Compose Glass | Flutter 3.0 的落地 | 说明 |
| --- | --- | --- |
| `rememberLayerBackdrop { drawRect(bg); drawContent() }` | `BackdropFilter` | 引擎把它落成 `BackdropFilterLayer`，采样的是「本层之前、在同一合成上下文里画过的内容」—— 语义与 `layerBackdrop` 一致。 |
| `Blur(4dp)` | `ui.ImageFilter.blur(sigmaX:, sigmaY:)` | sigma 单位是逻辑像素。 |
| `Lens(16dp, 32dp)` | `ui.ImageFilter.matrix`（仿射放大） | Flutter 3.0 没有 fragment shader 编译目标（`flutter_tools/build_system/targets/` 下无 shaders 目录），无法写真正的径向透镜 shader；只能用仿射矩阵把采样结果**放大**，等效「凸透镜把底下的内容顶大」。 |
| `onDrawSurface { drawRect(White.copy(0.5f)) }` | `ColoredBox(Colors.white.withOpacity(config.surface))` | 折射结果之上铺一层半透明白。 |
| `shape = { CircleShape }` / 胶囊 | `ClipRRect` / `ClipOval` | 轮廓收敛。 |

## 15.2 平台能力边界（实测，不是推测）

| 能力 | 原生（Skia） | Web（html renderer） |
| --- | --- | --- |
| 真实背景采样 | ✅ | ✅ —— 引擎把 `BackdropFilter` 落成 CSS `backdrop-filter: blur(Npx)`（实测 DOM 里确实生成了 `flt-backdrop-filter` 且带 backdrop-filter 样式） |
| 透镜折射（matrix） | ✅ | ❌ —— CSS 只认 blur，滤镜链里混入 matrix 会让**整个滤镜被丢弃**，玻璃退化成一层发脏的黑纱 |

所以配置被拆成三档（`GlassConfig`）：

- `blur` —— 卡片级模糊，**只在原生开**（一页几十张卡片，每张都做一次 backdrop
  采样会明显掉帧）；
- `navBlur` —— 导航级模糊（底栏 / 顶栏 / 侧栏），**两端都开**（只有几件大面积
  玻璃，采样收益最高）；
- `lens` —— 透镜倍率，**只在原生生效**，Web 恒为 1.0；
- `surface` —— 白色表面层不透明度。

> 这一版修正了上一版 README 里「Web html renderer 不启用 BackdropFilter」的
> **错误表述** —— 那条结论当时是推测，实测证明 html renderer 是支持的。

## 15.3 踩到的最大的坑：`RepaintBoundary` 会切断 backdrop 采样

第一版实现给玻璃套了一层自己的 `RepaintBoundary`，本意是「让滤镜坐标系等于
玻璃局部坐标」。结果原生截图里玻璃**完全不透底**，只剩一层浅紫。

用独立探针工程（同构复刻 `bottomNavigationBar` 结构）做左右对照后定位到根因：

| 玻璃外层 | 玻璃内能否看到背后的黑竖条（src x=250..260） |
| --- | --- |
| 套 `RepaintBoundary` | ❌ 完全看不到 |
| 不套 | ✅ 正常透出（250–259） |

原因是 `RepaintBoundary` 会为该子树建立**独立的渲染表面**，backdrop 采样只能
看到同一 surface 内、在本层之前绘制的内容 —— 背景全被隔离掉了。

**结论**：透镜支点不能用「给玻璃套 boundary」的办法解决。

## 15.4 最终方案：自定义 `RenderLensBackdrop`

新增 `app/lib/rendering/render_lens_backdrop.dart`，继承 `RenderProxyBox`，
在 **paint 阶段**构造滤镜：

- `BackdropFilter` 的 filter 是构造期常量，而支点必须知道「玻璃中心在滤镜
  坐标空间里的位置」—— 这个值只有渲染阶段才算得出来；
- 支点通过 `getTransformTo(最近一层 RepaintBoundary 祖先)` 把玻璃中心换算到
  **滤镜所在的空间**；没有 RepaintBoundary 祖先时退回根空间（屏幕坐标）；
- 玻璃本身**不套** `RepaintBoundary`，保证 backdrop 采样不被隔断。

配套新增 `app/lib/widgets/glass_sample.dart`（`GlassSample` / `GlassBlur`），
把采样层收敛成一个组件，底栏 / 顶栏 / 侧栏都走它。

## 15.5 `ImageFilter.matrix` 的坐标语义（像素级实测定论）

这几条是整块透镜最容易搞错的地方，全部用独立原生探针工程
（Linux + Xvfb，真实 Skia 渲染，读截图像素）测出来的：

1. **映射方向**是 `dest = s · src + t`，不是 `src = s · dest + t`；
2. **单位是逻辑像素**（dpr=2 时平移 100 逻辑 px 对应 200 物理 px）；
3. **坐标空间**是「滤镜所在的空间」= **最近一层 `RepaintBoundary` 祖先的局部
   空间**（没有则是根空间）；既不是控件自身局部坐标，也不是屏幕全局坐标；
4. **变换结果会溢出控件矩形**，必须靠滤镜**外侧**的 clip 收敛；
5. 让支点 p 不动的平移量是 `t = p · (1 − s)`。

### 实测数据一：支点在屏幕空间（无 RepaintBoundary 祖先）

背景一条黑竖条 src x=250..260，玻璃中心 x=300：

| lens | 实测黑条位置 | 理论值 `dest = pivot + s·(src−pivot)` |
| --- | --- | --- |
| 1.00 | 250–259 | 250–260（无位移） |
| 1.25 | 238–249 | 237.5–250 ✅ |

### 实测数据二：支点在有偏移的 RepaintBoundary 局部空间

玻璃被包在偏移 (100, 0) 的 `RepaintBoundary` 里（玻璃屏幕 x=100..260，
中心 x=180，边界局部中心 x=80），lens=1.25：

| 项 | 值 |
| --- | --- |
| 理论（局部空间计算） | local 167.5–178.75 → 屏幕 267.5–278.75 |
| 实测黑条位置 | **268–279** ✅ |

如果错误地拿屏幕坐标（180）当支点，结果会是 268.75 附近但整块玻璃朝错误
方向漂移 —— 这就是「支点必须在滤镜空间里」的意义。

这一轮把三件事落到了 Flutter 上：**共享 backdrop**、**弹簧按压回弹**、
**Hue 色相染色**。三件都不是「看起来像」就行的活儿 —— 每一件都先做了
像素级实测才动手写。

## 16.1 共享 backdrop：为什么不能「两件玻璃各采一次」

Compose 里两件玻璃引用的是**同一个** `rememberLayerBackdrop`，所以它们
看到的是完全相同的一份背景。Flutter 的 `BackdropFilter` 是逐层采样的，
直接照抄「每件玻璃一个 `BackdropFilter`」会出问题。

### 实测一：兄弟玻璃会互相采样

两块**完全重叠**的玻璃（上层 `lens=1.0, sigma=0.01`，下层内含 30×30 纯红块），
读上层玻璃内的像素：

```
x = 77, 85, 93, 101  →  全部是 (255, 0, 0)
```

上层玻璃把下层玻璃的纯红采进来了 —— **兄弟之间会互相采样**。

### 实测二：嵌套 `BackdropFilter` 的内层采样的是「外层的输出」

外层 `BackdropFilter(blur σ2)` + 内层 `lens=2.0` 玻璃，与「只有外层 blur」的
对照区并列，读同一条条纹序列：

| 区域 | 条纹周期 |
| --- | --- |
| 对照区（仅外层 blur） | 60 px |
| 内层 lens 区域 | **120 px**（正好 2 倍） |

内层透镜作用在外层模糊的**结果**上，而不是底层场景上。这正好是我们要的
语义（先共享模糊，再各自折射），但也带来一个新问题：**内层 matrix 的坐标
空间到底在哪一层？**

### 实测三：嵌套下内层透镜的支点在根空间

场景：外层 blur 覆盖 (100,200)–(800,400)，内层玻璃在屏幕 x∈[400,600]，
背景黑条在 x∈[450,470]。内层 `lens=2.0`。

| 支点假设 | 理论黑条位置 | 实测 |
| --- | --- | --- |
| **A：屏幕空间**，pivot = 500 | `dest = 2×460 − 500 = 420` | **实测暗段 401..439，中心 420** ✅ |
| B：外层滤镜局部空间（原点 100） | 屏幕 x ≈ 20（玻璃外，看不见） | 未出现 |

**结论**：嵌套滤镜下，内层 matrix 的 src/dest 仍在**根空间**，
`RenderLensBackdrop` 现有的支点换算逻辑（`getTransformTo(最近 RepaintBoundary
祖先)`，没有则退回根空间）对「外层 blur + 内层透镜」结构**依然是正确的**。

### 落地方案：一次采样 + 并集裁剪 + 各自透镜

```
Positioned.fill
  └ ClipPath(并集 = 胶囊 ∪ 圆形)          ← 只有这块形状可见
      └ BackdropFilter(blur = navBlur)     ← 全底栏**唯一**一次背景采样
          └ Stack
              ├ ClipRRect(胶囊)  → GlassSample(lens)   ← 各自透镜
              └ ClipOval(圆形)   → GlassSample(lens)
```

- **一次采样**：两件玻璃看到的是**完全相同**的一份背景，彼此不会互相采样；
- **并集裁剪**：用一条 `Path`（胶囊 RRect ∪ 圆形 Oval）把模糊结果裁成两件
  玻璃的形状；
- **各自透镜**：每件玻璃在共享的模糊结果上再叠一层 matrix，支点各在自身
  中心，等效 Compose 里每件玻璃各自的 `Lens(16, 32)`。

布局从 `Row` 改成了 `Stack` —— `Row` 给不出两件玻璃的精确矩形，而共享
采样层必须要。

## 16.2 弹簧按压：回弹要作用在**玻璃本体**上

Compose 参考里 `layerBlock { scaleX = 比例; scaleY = 比例 }` 改的是
`background` 绘制层的缩放 —— 也就是**玻璃形状本身**在变大，图标只是躺在
上面。

第一版实现只放大了内容层（图标），玻璃形状纹丝不动 —— 手感完全不对。
这一轮改成：按压进度直接参与**几何计算**，圆形玻璃的矩形、共享采样的
并集裁剪路径、表面层与内容层**全部**随弹簧进度一起长。

| 项 | Compose | Flutter |
| --- | --- | --- |
| 最大倍率 | `(size.width + 16dp) / size.width` | 同 |
| 弹簧 | `spring(dampingRatio = 0.5f, stiffness = 300f)` | `SpringDescription.withDampingRatio(mass: 1, stiffness: 300, ratio: 0.5)` |
| 驱动 | `animateTo(1f)` / `animateTo(0f)` | `SpringSimulation` + `AnimationController.unbounded` |

用 `unbounded` 控制器是刻意的：**过冲是液态手感的来源**。弹簧会冲过目标值
再回弹，有界控制器会把过冲截断 —— 而单测里正是断言了 `progress` 会
出现 `> 1` 的值。

按压放大的溢出部分需要画布留余量：整块底栏被放进一块比自身大一圈
（`_pad = 14`）的画布里，圆心固定、尺寸按倍率长，溢出部分仍留在画布内。

## 16.3 Hue 色相染色：不透明色会把玻璃变成色板

`BlendMode.hue` 取**源**的色相、**目标**的饱和度与明度。实测（原生
Skia）：底层红 `(255,0,0)` + 玻璃内 Hue 蓝 → 结果 `(0,97,174)`，正是
「蓝的色相 + 红的饱和度明度」，证明 Hue 确实作用在滤镜输出上。

但照抄 Compose 的 `drawRect(tint, blendMode = BlendMode.Hue)` —— 那个
`tint` 是**不透明**的 —— 后果是灾难性的：色相被**整体**接管，整块玻璃
变成一整块不透明的蓝色板，背景一点也透不出来。那已经不是玻璃了。

原生截图对比（同一帧）：

| 版本 | 观感 |
| --- | --- |
| 不透明 Hue 源 | 胶囊 = 一块死板的蓝色渐变，完全不透明 |
| **半透明 Hue 源**（`hueMix = 0.22 × 强度`） | 玻璃通透，能看到背后的卡片透上来，色相偏冷 |

所以 `GlassConfig` 加了第三个染色参数：

| 字段 | 对应 Compose | 取值 |
| --- | --- | --- |
| `hue` | `val 色调 = 颜色(0xFF0088FF)` | `Color(0xFF0088FF)` |
| `hueMix` | `drawRect(tint, BlendMode.Hue)` 的**源不透明度** | `0.22 × 强度` |
